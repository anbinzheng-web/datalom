# 数据桶与采集架构

## 已接受的存储方案

导出格式是派生能力，不是规范化存储格式。系统采用三层数据模型：

1. 原始响应以压缩 JSONL 归档，保留采集证据和重跑解析所需的信息。
2. 清洗、去重和标准化后的数据以 Parquet 作为主存储格式。
3. SQLite/PostgreSQL 只保存控制面元数据；JSON、JSONL、CSV、SQLite、训练集等格式由异步导出任务生成。

这意味着用户可以灵活选择下载格式，而采集流程不需要围绕某一种交付格式设计。

## 在线库和数据桶分离

`.datalom` 是在线控制面数据库：账号会话、任务队列、租约、诊断和短期结果。它适合小事务和本机管理，不适合承载 1GB 级可下载数据集。

可售数据集使用独立的 **数据桶（data bucket）**，一个桶是一个不可变版本目录或归档包：

```text
bucket-id/
  manifest.json       # schema、版本、行数、字节数、校验和、生成时间
  parquet/            # 规范化数据的主存储
  raw/                # 原始压缩 JSONL，可选按权限交付
  data.sqlite         # 可选导出，适合需要 SQLite 查询的用户
  parts/000001.ndjson.zst
  parts/000002.ndjson.zst
  checksums.sha256
```

Parquet 是规范化数据的共同来源。小桶可以额外交付 `data.sqlite`；大桶优先使用压缩、可校验、可并行下载的分片文件。发布前先写临时目录，完成校验后原子 rename 到版本目录，禁止在线采集器修改已发布桶。SQLite 导出使用 WAL checkpoint 和只读副本，避免复制正在写入的数据库。

在线库只保存桶的 manifest、状态、分区信息、导出任务和下载授权，不把大字段写进 API 响应。下载接口应支持 HTTP Range、ETag、断点续传和流式传输；应用容器不把大桶读入内存。

控制面通过 `ObjectStore` 抽象访问文件。Docker 单机阶段使用本地数据卷实现；多节点阶段切换到 S3 或 MinIO，不改变数据集和导出逻辑。

## 采集器隔离

采集器分为调度器和执行器。调度器创建采集批次、分片和租约；执行器使用平台适配器获取数据，先写本地临时原始桶，再清洗、去重并生成 Parquet，最后批量提交 manifest。采集任务不直接占用面向用户的 API 连接池。

用户导出通过异步 `export_job` 完成：导出 Worker 从 Parquet 扫描数据，生成 JSON、JSONL、CSV、SQLite 或训练格式，写入新的不可变 artifact 并返回下载信息。API 请求不现场转换 GB 级数据。

默认优先直接调用共享的 `packages/platform-*` 执行层，而不是回环调用公网 API。若为了权限、审计或版本隔离而调用 API，必须使用独立的内部入口、连接池、限流额度和队列，不能与用户请求共用并发上限。用户 API 只负责提交/查询任务，采集执行应由独立 worker 或独立部署单元承载。

## Docker 存储约定

容器使用 `DATALOM_DATA_DIR=/data`，SQLite 和密钥依赖挂载卷持久化。生产环境应把数据桶挂载到单独的对象存储同步目录或专用卷，不要把桶打进镜像，也不要把 SQLite WAL 文件放在临时容器层。备份按 manifest 校验和验证，恢复时先恢复在线库，再重新索引数据桶。
