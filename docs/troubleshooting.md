# 问题排查与证据链

Datalom 的目标是每次失败都可追踪、可解释、可继续实验。允许问题暂时未解决；不能把未知原因编成已确认原因，也不能靠重复请求掩盖失败。

## 日常入口

「请求与任务 → 结果与排查」包含执行时间线、排查表单和独立的「导出排查报告」。管理服务、提取和线路验证事件在「接口研究 → 服务排查记录」。错误响应中的 `diagnosticId` 可直接定位原始异常。

状态：待排查 → 排查中 → 待实验条件 / 已解决。原因分为尚未确认、待验证推测、有证据确认。未解决的问题必须填写下一步实验；修改有版本校验与追加历史，旧判断不删除。

标记已解决必须填写原因、修复内容，并关联**问题发生后、同账号、同业务操作的成功任务**。这保证存在回归依据；还需在修复说明中写清视频、页数、对照变量和验证范围。单次成功不等于永久稳定，测试环境成功不等于真实 TikTok 成功。

## 固定流程

1. **Inspect：记录发生了什么。** 使用任务 ID / 请求 ID 找到开始时间、账号、会话版本、操作、截止时间、页码、尝试次数和最后执行阶段。保存现场，不先覆盖会话或删除失败记录。
2. **定位事实。** 读取对应事件的加密原文。检查请求是否发出、代理是否建立、HTTP 状态与响应内容、业务解析结果、签名输入版本、底层异常及 cause。HTTP 200 不自动代表成功。
3. **建立推测与实验。** 写下当前为什么失败、哪些证据支持、哪些事实仍不知道，制定一次只改变必要变量的实验。NETWORK / CHALLENGE 等分类只是观测，不代表已经证明网络或账号根因。
4. **Replay / Debug。** 用新的任务和新签名验证同一业务输入。生产重放不调用浏览器，也不重放过期的固定签名。需要浏览器时走显式研究流程，记录浏览器研究与独立执行的区别。
5. **修复与回归。** 记录修改内容、对应测试及回归任务 ID。必要时比较旧会话快照、脚本哈希、SDK 版本与响应差异。正常结果和失败结果均保留。
6. **Diagnose：写回结论。** 根因尚未确认就保持未确认；实验条件不足就记录阻塞条件和下一步。不允许只报一句“失败了”而不留排查依据。

## 已持久化的内容

| 层级       | 证据                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| 任务与调度 | 提交、领取、排队时间、频率等待、取消请求、重试理由、页码、游标、去重数量、完成/失败、清理                                 |
| 执行环境   | 账号和会话版本、当时的完整加密会话快照、代理配置与线路哈希、适配器和网络配置、Node 版本、系统架构、PID                    |
| 签名       | 输入阶段、计数器、参数更新、样本时间、脚本哈希、新签名请求；异常栈、签名子进程退出码和 stderr 尾部                        |
| 网络       | 实际请求 URL 和请求头（包括 Cookie，仅存密文）、响应头与全部 Set-Cookie、状态、响应体、字节数、耗时、部分响应与原始错误链 |
| 代理       | GOST PID、启动/结束、退出码、完整 stderr 分块加密记录；结束摘要保留最后 64 KiB，明确标出截断                              |
| 恢复       | Worker 启停、服务端观察到的 Worker 退出、过期租约导致的中断、排队超时；最后成功记录的阶段仍保留                           |
| 管理       | 提取/验证/配置等管理操作的请求 ID、路径、方法、参数与输入（加密）、返回状态、异常栈；不记录登录令牌输入                   |
| 人工结论   | 事实、原因确认程度、下一步实验、修复说明、回归任务、修改时间与历史版本                                                    |

原文使用 AES-GCM 加密；时间线含 SHA-256 原文摘要。网页和普通报告不返回原始请求、Cookie、Token、代理密码、异常栈。文本结论会遮盖已知会话秘密及常见认证格式，但不要把凭据写入自由文本；原始异常始终放在加密事件中。

网络响应上限仍为 20 MB。超过声明大小会在读体前停止并保留响应头；流式超过上限或读取中断会保留已读取部分及截断标志。签名进程 stderr 尾部上限 64 KiB，记录总字节数与截断标志。这些限制会显式留下证据缺口，不冒充完整捕获。

## 本机命令

```sh
pnpm diagnose inspect <taskId>   # 任务、问题状态和时间线摘要
pnpm diagnose events             # 最近 200 条事件摘要
pnpm diagnose raw <eventId>       # 将单条事件原文解密到本机受限文件
pnpm diagnose emergency          # 解密紧急日志到本机受限文件
pnpm diagnose replay <taskId>    # 明确提交一次新任务，使用当前会话与新签名
```

`raw` / `emergency` 输出文件位于 `.datalom/diagnostics/exports/`，目录权限 0700、文件 0600；终端只打印文件路径。文件可能包含凭据，仅用于本机排查，不要上传或共享；完成后按需删除该导出副本，加密原始证据继续保留。系统密钥库和原数据库必须一起保全，遗失主密钥无法解密。

`replay` 不会覆盖原任务，不会解除登录暂停或代理约束，也不会无限重试。需要注意它仍会发起真实生产请求。旧任务可查看原有结果，但升级前没有记录的时间线无法补造。

内部接口：`GET /api/tasks/:id/diagnostics`、`PUT /api/tasks/:id/diagnosis`、`GET /api/diagnostics/events`，均使用现有本地鉴权及 Origin/Host 校验。没有解密原文的网页 API。

## 日志本身出错时

关键事件同步写入 SQLite WAL。任务入队和提交事件、任务成功与成功事件在事务中一起提交。诊断写入失败时，不继续发送未记录的生产请求；Worker 停止领取并中止在途任务，健康心跳撤销。

数据库写入失败会尝试写入独立 `.datalom/diagnostics/emergency.jsonl`，原文同样加密，每条追加后 `fsync`。若紧急文件也不能写，stderr 输出固定的 `DATALOM_DIAGNOSTICS_UNAVAILABLE` 并停止执行，不声称保存成功。进程异常由紧急日志记录；SIGKILL 或断电不能运行退出回调，由下一次恢复记录租约中断，保留最后阶段。原始操作系统杀进程原因仍可能需要系统日志佐证。

目前不自动删除诊断证据；应定期检查磁盘空间、备份数据库与密钥，避免磁盘耗尽。网页报告不包含加密原文。尚未做长期容量评估、磁盘物理损坏恢复或整机断电实测。

## 验证范围

新增故障注入覆盖重试与原始 cause、会话快照关联、无敏感明文落盘、诊断版本冲突、错误关闭问题、排队超时、过期租约与诊断数据库不可写。界面使用独立 fixture 验证排查结论保存、重新打开与导出。

这些是离线和受控验证。本次诊断增强不把它们冒充真实平台故障恢复；已有双账号 TikTok 结果见 `validation.md`。
