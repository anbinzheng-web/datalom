# 钱包与每日调用费用

范围：个人钱包、幂等资金流水和按 API Key 的每日费用统计存储。支付渠道、支付订单、充值回调校验、定价、用户 API Key 鉴权、在线余额检查与实际扣费尚未接通，不因表结构存在而宣称已上线。

## 数据模型

新增三张表，不增加逐调用数据库日志表：

| 表 | 内容 | 约束 |
| --- | --- | --- |
| wallets | userId、currency、balanceMicros、createdAt、updatedAt | 一人一个钱包，余额不为负，币种创建后固定 |
| wallet_transactions | UUID、userId、type、reference、amountMicros、balanceAfterMicros、apiKeyId、usageDate、calls、failedCalls、createdAt | type 为 topup 或 usage；同类型 reference 全局唯一；充值正金额，调用结算为负金额或零 |
| api_usage_daily | userId、apiKeyId、usageDate、calls、failedCalls、costMicros、updatedAt | 每个用户/Key/日期一行，复合外键确保 Key 归属用户 |

当前默认币种为人民币 CNY，一个用户只使用一种币种，不进行自动换汇。金额使用 BIGINT 整数，1 单位币种 = 1,000,000 micros。不使用浮点运算，未来 JSON 接口必须返回十进制字符串以避免 JavaScript 大整数精度损失。钱包仅存已入账余额；待付款订单不作为充值流水，也不直接修改余额。

日期按 UTC 自然日统计。统计包含总调用数、失败调用数及实际扣费总额；是否对失败请求收费由尚未实现的定价层决定，存储层不推断价格。用户总费用由各 Key 汇总，无需再维护一份用户日表。Key 改名或撤销不改变历史归属；有账务数据的用户及 Key 不允许物理级联删除。

## 一致性与并发

充值入口将来必须验证支付渠道结果，再使用稳定的渠道订单标识作为 reference 调用入账；当前仅提供内部存储能力，不提供直接充值公开接口。

结算接口接收已经归属到用户、Key 和 UTC 日期的汇总批次。每个批次使用稳定且唯一的 reference。余额条件更新、资金流水和每日统计在同一个 PostgreSQL 事务内完成；重复提交相同内容返回原流水，reference 复用为不同内容时拒绝。余额不足则整个事务回滚，不生成半套账目。不同用户不共享全局事务锁，同一用户的余额更新仍由数据库行锁串行化。

未来高并发计费应从可靠投递的结算记录批量入账，不能仅靠易失内存累计或普通诊断日志恢复资金。可靠投递、单次调用去重、价格版本、预授权/余额预留、断线补偿、跨节点透支控制及拒绝欠费请求尚未实现。批次 reference 只能防止同一批次重放，不能识别不同 reference 下重复包含的调用。

## 数据保留

每日调用费用统计保留滚动最近 12 个日历月（UTC 日期，月末向目标月最后一天截断），不按固定 365 天计算。早于边界的统计删除，边界当天保留。查询同样限制保留窗口，防止清理延迟暴露更早的数据。

钱包余额与资金流水不随统计清理删除，用于幂等充值、防重扣费和余额核对。删除每日统计不会返还已消费金额。API Key 不允许改归属或物理删除以破坏账务关联，应使用 revokedAt 撤销。

server 启动及每小时执行一次统计清理，每批 1000 行，每次最多 10 批，跨进程使用 SKIP LOCKED。清理不放在请求路径；仅删除 api_usage_daily 的过期行，不改动其他业务数据。服务停机时不执行清理，恢复后继续；失败输出 DATALOM_USAGE_RETENTION_FAILED 并在下一周期重试。超过单次上限的积压分多次清理，查询仍严格限制 12 个月窗口。
