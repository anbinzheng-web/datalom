测试视频：`7669255703952985375`，页面作者 `prettypickedd`；独立详情返回同一 ID、作者、描述以及评论计数 422，与页面取证一致。

其他真实观测：一个少评论视频返回 9 条、`has_more=0`；Worker 能正常停止分页。独立签名每次生成，不使用浏览器签名服务。当前验证覆盖签名 5.3.2 / SDK 2.0.0.561，不能直接外推到未来 SDK 或所有 TikTok 账号。

## 代理与请求差异实验

- 两个账号均通过 GOST → Clash → Profile SOCKS5 出站，独立检测出口与各自 Profile 记录一致。
- 受控双代理记录证明先连接上游，再连接账号代理，最后抵达目标。
- 第一跳关闭后，再发请求不能抵达目标，没有直连回退。
- `impit` 通用 chrome preset 返回 200 空响应；chrome151 + 对应会话请求头和独立签名返回正常 JSON。
- 直接新开某个视频页曾返回维护页；从已有搜索页的实际交互捕获到了成功请求。失败页面和后续成功请求均保留为证据。

这证明请求路径和目标接口兼容性；未完成逐字节 TLS/HTTP2 指纹一致性、Clash TUN 特殊路由或动态代理切换专项测试。

## 受控基准

首次测量：本机受控 HTTP/1.1 双跳，1 KiB JSON，每档 200 请求。并发 1/5/10/20 分别约 1527/4541/4822/5084 req/s，P95 1.27/1.52/3.90/5.11 ms。

报告 `artifacts/benchmark.json` 明确测量范围：Node 客户端与 GOST 转发，不包含真实平台延迟和限流，不是 impit TLS/HTTP2 端到端基准；CPU/RSS 不包含 GOST 进程。不可据此宣称 TikTok QPS。

## 尚需长期验证

- 超过短期实验窗口后的 Token 更新和会话过期。
- 更多视频、账号地区和分页边界；当前真实双账号回归使用同一公开视频。
- 10–50 账号的持续运行、生产请求压力和每次成功调用成本。
- Firefox/BiDi、关键分区 Cookie、其他签名版本及新平台。
- Windows/Linux 密钥库与平台二进制部署。

研究失败不删除。响应为空、业务状态非零或未知签名布局会保留诊断证据，不能计入成功任务。
